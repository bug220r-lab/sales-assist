# 1. Database location and filesystem safety

The active database must not default to the Git repository or a OneDrive-synchronized directory.

Use an application data root under the current user's local application-data directory, equivalent to:

```text
%LOCALAPPDATA%\SyntheticSalesAssist\
```

Recommended layout:

```text
%LOCALAPPDATA%\SyntheticSalesAssist\
├── data\
│   └── synthetic_sales_assist.sqlite3
├── logs\
├── backups\
├── runtime\
└── exports\
```

Requirements:

- no administrator privileges;
- deterministic path resolution;
- optional explicit `--data-dir` override for testing and isolated instances;
- override must resolve to a local filesystem path;
- reject network shares, UNC paths, URLs, device paths, and traversal;
- repository tests use isolated temporary directories;
- never write runtime database/log/backup files into `specs/`, `reference/`, fixtures, or Git-tracked paths;
- `.gitignore` covers local runtime artifacts;
- active database file is not synchronized by default.

Document the path policy.

# 2. SQLite connection and integrity policy

Use Python's standard-library SQLite unless an already-installed approved dependency provides a clear benefit without network installation.

Required connection behavior:

- `PRAGMA foreign_keys = ON`;
- explicit transaction boundaries;
- bounded busy timeout;
- deterministic row/text handling;
- no implicit autocommit for multi-step business operations;
- startup schema-version verification;
- application/version metadata;
- transactional migration application;
- rollback on migration failure;
- `foreign_key_check`;
- `quick_check` for ordinary health;
- `integrity_check` for explicit deep verification.

Codex may choose and document:

- rollback journal versus WAL;
- connection-per-operation versus managed connection;
- writer serialization;
- read transaction strategy;
- index plan;
- trigger use.

Create an ADR for the selected SQLite concurrency/journal/transaction strategy.

Tests must prove:

- foreign keys are active on every application connection;
- concurrent reads are safe;
- concurrent writers preserve idempotency and event ordering;
- no partial transaction survives injected failure;
- a database opened with an unsupported future schema version fails closed.

# 11. Backup and restore

Use SQLite's online backup API, `VACUUM INTO`, or an equally safe SQLite-supported mechanism.

Do not copy an open database file byte-for-byte as the primary backup method.

Each backup must include:

- backup file;
- sidecar metadata or embedded receipt;
- source database schema version;
- application version;
- source database SHA-256 after a consistent backup boundary where meaningful;
- backup SHA-256;
- created-at timestamp;
- row/table summary;
- quick-check and foreign-key-check status.

Backup path rules:

- local filesystem only;
- reject URL, UNC/network share, device path, and traversal;
- create parent directory only when explicitly safe;
- never overwrite an existing backup without explicit `--overwrite`.

Restore requirements:

1. Verify backup file and receipt.
2. Open the backup separately.
3. Run quick/integrity and foreign-key checks.
4. Verify schema compatibility.
5. Create an automatic pre-restore backup of the active database.
6. Restore into a temporary file.
7. Verify the temporary restored database.
8. Atomically replace the active database.
9. Reopen and verify the active database.
10. Roll back to the pre-restore backup if any post-swap verification fails.

Restore requires `--confirm`.

Tests cover:

- empty/new DB;
- populated DB;
- corrupt backup;
- wrong checksum;
- unsupported future schema;
- interrupted restore;
- exact restore;
- restore followed by exact replay;
- active database remains valid after rejected restore.
